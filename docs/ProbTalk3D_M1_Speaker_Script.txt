ProbTalk3D - Milestone 1: Code Review and Understanding
Speaker script (two presenters: P1 and P2). Not part of the slides.

--- Slide 1: ProbTalk3D ---
P1: Hi everyone. This is our progress update for ITCS 6166, Generative AI as a Service. Our paper is ProbTalk3D. It takes a speech recording and turns it into an animated 3D face, with emotion, and it gives a slightly different performance every time you run it. This update is Milestone 1, code review and understanding. We walk through how the repository is organized, how a run is configured, and the key pieces of code that make the paper work: the two training stages, the sampling step that makes it non-deterministic, the losses, and the inference script. We finish with what the review found and our plan for Milestone 2, running the model in Google Colab.

--- Slide 2: Project status ---
P1: Here is where we are. The proposal, Milestone 0, is done: we selected and presented the paper. Milestone 1, code review and understanding, is this update. We read the repository and traced how a run works, from the command line to the saved output. Next is Milestone 2, running the authors' pretrained model in Google Colab. After that, Milestone 3 is the service: the model hosted in the cloud with a client app. The two bonuses, a phone app and training on the university cluster, are stretch goals we will decide on after Milestone 2.

--- Slide 3: From speech to a moving face ---
P1: Here is the whole model in one picture. Speech goes in on the left. HuBERT, a speech model, turns the audio into numbers that describe the sound. A predictor network combines those with a style: which speaker, which emotion, and how intense. The predictor does not draw a face directly. It chooses entries from a codebook of 256 learned facial motions, like picking from a dictionary of expressions. A decoder rebuilds the full motion from those entries, and the result is a file of FLAME face parameters. Training happens in two stages. Stage 1 learns the dictionary from real face data, with no audio. Stage 2 learns to pick from the dictionary given speech and style, while Stage 1 stays frozen. The key idea is at generation time: instead of always taking the closest entry, it draws one at random, weighted by closeness. That is why every run is different.

--- Slide 4: Repository map ---
P2: Now what we learned from reading the code. This is the repository map. train_all.py is the training entry point and handles both stages. generation.py is the inference entry point: audio files in, face motion out. It is the file we will run in Milestone 2. The configs folder holds the Hydra configuration files that decide what a run looks like. The framework folder holds the model code: the two-stage model, the predictor and the HuBERT wrapper. The datasets folder has the normalization scalers, the splits and the FLAME templates. The render scripts turn motion into video, using Blender or a pyrender version. There is also a diffusion folder, a modified FaceDiffuser that the authors use as a comparison baseline. It is not part of the main pipeline.

--- Slide 5: How a run is configured ---
P2: The first thing to understand is the configuration system, Hydra. Nothing is hard-coded in the scripts. On the command line you pick the pieces: the experiment, the data and the model. The model's config file then names a Python class with the underscore-target line, and lists its parts under defaults, for example the encoder and the decoder. You can also see the codebook size here: 256 entries of 128 numbers each. When the code runs, it calls instantiate on the config and Hydra builds the model. For generation, the script loads the config saved with the trained model and merges our command-line overrides on top. That means in Milestone 2 we can change the temperature, the style and the deterministic switch from the command line, without touching the code.

--- Slide 6: Stage 1: the motion autoencoder ---
P2: Now Stage 1 in the code, the motion autoencoder. In the forward pass it is three lines. The encoder takes real face motion and compresses it into one latent vector per frame. The quantizer snaps each vector to its nearest entry in the codebook, our dictionary of 256 facial movements. The decoder rebuilds the motion from those entries: 53 numbers per frame, 50 for expression and 3 for the jaw. The quantizer is created with beta 0.25, which weights the commitment loss that keeps the encoder's output close to the dictionary. Stage 1 never sees audio. It only learns what realistic face motion looks like.

--- Slide 7: Where the randomness lives ---
P2: This is the most important piece of code in the repository, because it is what makes the model non-deterministic. It lives in the vector quantizer. First the code measures the distance from each frame's latent vector to all 256 codebook entries. Then there is one if/else. If sampling is off, which is always the case during training, it takes the closest entry with argmin. If sampling is on, it turns the negative distances into probabilities with a softmax, after dividing by a temperature, and then draws an entry at random with torch.multinomial. So close entries are likely but not guaranteed, and each run can pick a different sequence of entries. Temperature controls how adventurous that draw is. At a low temperature it almost always picks the nearest entry. At a high temperature the probabilities flatten out and you get more variety. The default in generation.yaml is 0.2, and the README recommends 0.1 to 0.5. There is also a switch, sample=false, that turns the randomness off completely.

--- Slide 8: Stage 2: speech and style to motion ---
P1: Stage 2 is where speech comes in. This is the forward pass, simplified to fit on a slide. HuBERT turns the audio into 768 numbers per frame, at 50 frames per second. The video runs at 25 frames per second, so the code simply joins every two audio frames into one vector of 1536 numbers. A linear layer maps that down to 256. The style, meaning which speaker, which emotion and which intensity, is a one-hot vector with 43 slots: 32 speakers, 8 emotions and 3 intensities. Another linear layer turns it into 256 numbers, and the code multiplies it with the audio features, so the style scales every frame. Then a small convolution and a 12-layer transformer predict a latent for each frame. Those predictions go through the same quantizer from Stage 1, which is where the sampling happens, and the Stage 1 decoder turns them into the 53 motion numbers. Stage 1 is loaded from its own checkpoint in eval mode and its weights are frozen, so Stage 2 only learns to land on the existing codebook.

--- Slide 9: How each stage is trained ---
P1: Here is how each stage is trained, read straight from the loss configs. Stage 1's total loss is 1.5 times the quantization loss, plus 0.5 times the L1 error on the 50 expression values, plus 0.1 times the L1 error on the 3 jaw values. The quantization loss has two parts: one pulls the codebook entries toward the encoder's output, and one, weighted by beta 0.25, keeps the encoder committed to the codebook. Because picking the nearest entry has no gradient, the code uses the straight-through trick, z plus the detached difference, so gradients still flow back to the encoder. Stage 1 uses AdamW with a learning rate of 1e-4. Stage 2's main loss compares the latent codes it predicts from speech with the codes Stage 1 produces for the real motion, plus smaller reconstruction terms on expression and jaw. It uses Adam with a lower learning rate, 1e-5. Both stages stop early if the validation loss does not improve for 5 epochs. One small thing we noticed: the training script still labels the Stage 2 latent loss "crossEntropy" in its logs, but the code actually computes an L1 loss.

--- Slide 10: Tracing generation.py, step by step ---
P2: This is generation.py, the script we will run in Milestone 2, traced from start to finish. First it loads the configuration that was saved with the trained model and merges our command-line settings on top. Second, it builds the model with Hydra's instantiate, and moves it to the GPU if there is one. Third, it loads the checkpoint, switches to evaluation mode, and sets the temperature and k. Fourth, it reads each audio file at 16 kilohertz and normalizes it. Fifth, it picks a style for each clip: speaker, emotion and intensity. If we do not give one, it picks at random. Sixth, the model runs and produces 53 numbers per frame. Seventh, the values were normalized during training, so the script undoes that with two saved scalers, one for expression and one for jaw. Eighth, it pads the result into the full FLAME layout: 300 shape values, which stay zero, 100 expression values, of which the model fills 50, and 3 jaw values, for 403 in total, and saves it as a .npy file. The important takeaway is that the output is numbers, not a video. Rendering is a separate step.

--- Slide 11: Six things to plan for in Milestone 2 ---
P1: While reading the code we found six things to plan for before we run it. First, the versions are old and pinned: the README targets Python 3.9 and PyTorch 2.1.1, and requirements.txt freezes 182 exact packages, including transformers 4.10. Google Colab today runs much newer versions. Second, the repo ships its own copy of the HuBERT model code, and that copy imports transformers.deepspeed, a module that newer versions of the transformers library no longer have, so we expect that import to need a fix. Third, the checkpoint is loaded with torch.load without the weights_only argument, and PyTorch 2.6 changed its default, which can block loading checkpoints that store extra objects. Fourth, a small documentation mismatch: the README's troubleshooting section mentions the HuBERT x-large model, but the config actually loads hubert-base as the audio model, which matches the 768 features per frame we saw in the code. Fifth, the model only handles one clip at a time; that is fine for a demo but matters for a service. Sixth, the pretrained weights live on Google Drive, and making a video needs a separate renderer, Blender or pyrender. These six points are our checklist for Milestone 2.

--- Slide 12: Milestone 2: run it in Google Colab ---
P2: Finally, our plan for Milestone 2, replicating inference in Google Colab. Step one: start a GPU runtime, clone the repository and download the authors' pretrained weights. Step two: install only the packages generation.py actually needs, instead of the whole frozen requirements list, and fix the issues from the previous slide as they come up. Step three: run generation on the eight test clips that ship with the repo and check that the output has the shape we traced. Step four: test the paper's main claim. We will run the same clip and the same style several times and check that the outputs differ, sweep the temperature to see whether variety grows with it, and confirm that sample=false makes the output identical every time. Step five: render the FLAME numbers into a face video so we can actually see it. After that, Milestone 3 is hosting the model on Hugging Face Spaces with a client app. Thank you, and we are happy to take questions.
